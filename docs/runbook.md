# 障害対応ランブック — kSQL Flow バッチ（雛形）

> このファイルはテンプレートです。**自分の運用に合わせて書き換えてから**、ログアプリの「アプリの説明」から自リポジトリのこのファイルへリンクしてください（テンプレート付属のアプリ説明文にあるランブック URL は、作者の環境のものなので必ず差し替えること）。

通知を受けたら、このページの該当節だけ読めば動けるようにしてあります。
（設計上の根拠は [ksql-flow 公開仕様書 §5.5](https://github.com/rex0220/ksql-flow/blob/main/docs/ksql_flow_spec.md)）

> **前提環境**: 本ランブックの具体手順は**現在の運用構成 = VPS（cron + リラン指示ポーラー）**を前提に書いています。Windows タスクスケジューラ（連載 #4）や GitHub Actions（#6）で運用する場合の差分は、各節の「他環境の場合」を参照してください。

## 1. 失敗通知（FAILED / ABORTED）

通常の失敗対応です。**慌てる必要はありません** — 書く前に止まる設計です。

1. 通知のリンクからログアプリのレコードを開き、`エラー内容` を読む
2. **ABORTED（業務データ起因）**: 原因データを直してから、そのレコードの**「リラン要求」にチェック**（5 分以内に自動リラン）
3. **FAILED（基盤起因）**: 基盤の回復を待って同じくチェック。詳細は連載 [#7](https://qiita.com/rex0220/items/39821af2a79b88de0ed2) / [#8](https://qiita.com/rex0220/items/30cac8d8b52ec8ac782a)

## 2. リラン滞留（ポーラー停止の可能性）

チェックを入れたのに 1 時間処理されていない状態です。**ポーラーは VPS でのみ運用しているため、この通知の対応先は常に VPS です。**

1. VPS へ SSH: `ssh root@<VPS>` → `grep CRON /var/log/syslog | grep poll_control | tail -3`（5 分ごとに動いているか）
2. 動いていなければ: `crontab -l` で行の有無を確認 → `tail /var/log/ksql/poll-control.log`
3. ポーラーを復旧すれば、**チェックは入ったままなので次のポーリングで自動処理**されます（再チェック不要）

## 3. ハング（実行中のまま更新停止）

**まずリランしない・チェックも入れない。** 手順は 3 つだけです（**VPS の場合**）。

1. VPS へ SSH し、対象プロセスを確認:
   ```bash
   ps aux | grep -E "run_batch|ksql-flow" | grep -v grep
   ```
2. ハングしているプロセスを停止:
   ```bash
   kill <PID>        # 効かなければ kill -9 <PID>
   ```
3. **以上で終わり。** 次回の定期実行（または 5 分後のポーラー）が stale を自動回収して正常化します。
   その際 **TIMEOUT の失敗通知が 1 通飛びますが、これは正常な回収の記録**です。回収後の実行が SUCCESS ならば復旧完了。

> プロセスが**見つからない**（すでに死んでいる）場合も同じ — 何もしなくても次回実行が自動回収します。

**他環境の場合**:
- **Windows タスクスケジューラ**: PowerShell で `Get-Process node` → `Stop-Process -Id <PID>`（またはタスクマネージャーから node を終了）。以後は同じく次回実行が自動回収します
- **GitHub Actions**: 実行環境が使い捨てのため「生存ハング」は起きません — Actions 側のジョブタイムアウトか手動キャンセルで runner ごと消え、残った RUNNING レコードは次回実行が stale 回収します（対応不要）

## 4. TIMEOUT（stale 回収が起きた）

次回実行が前回のハング/クラッシュを回収した合図です。**多くの場合、対応不要**です。

1. 回収後の実行（同じ通知の直後のバッチ）が **SUCCESS になっていればそれで完了** — データは冪等リランで収束済み
2. 回収後の実行も失敗していれば → [1. 失敗通知](#1-失敗通知failed--aborted) の手順へ

### ⚠ フル手順が必要な場合（まれ）

**GitHub Actions や別サーバーなど、この VPS 以外の起動元を併用しているとき**に TIMEOUT が出た場合だけは、回収された旧プロセスがまだ生きている可能性があります（古いデータを書き戻すリスク）。その場合:

1. 全スケジュール（cron・ポーラー・Actions）を一時停止
2. ログの `実行ホスト` / `開始日時` から旧保持者のホストを特定
3. **そのホストでプロセスの停止を確認**（生きていれば止める）
4. 確認できたら: リラン（チェック）またはバックフィルで復旧 → 突合 → スケジュール再開
5. 停止を確認**できない**場合: リランを重ねず、静穏期間を置いてから全量再計算 + 突合

**現在の運用（この VPS 単独）ではこのケースは構造的に発生しません** — ローカルロックが生存中のプロセスから奪わないためです。

```bash
# ロック状態の確認と手動解除（一覧を確認してから）
node --env-file=.env node_modules/@rex0220/ksql-flow/dist/cli.js unlock --profile prod

# 手動リラン（SSH 経路 — kintone のチェックと同じ動作）
./run_batch.sh --resume
```
